# Unified Evaluation Protocol

This replaces the earlier mix of `evaluate_all.py` (2 questions, real Ragas, 6 baselines) and
`evaluate_graph_comparison.py` (6 questions, a word-overlap heuristic labelled "faithfulness", 4 systems).
Numbers from those two scripts should not be put in the same table, and should not be reported as Ragas.

## What is compared

| Key | System | Notes |
|---|---|---|
| `naive` … `multimodal` | The 6 baselines in `src/engine.py` | via `RAGEngine.query_architecture` |
| `htree` | Hierarchical Tree RAG (proposed) | same engine |
| `workflow` | Workflow GraphRAG / Process DAG (proposed) | same engine |
| `llm_only` | Generator with no retrieval | lower bound; shows what pure-LLM answers look like |
| `full_context` | All 7 SOPs pasted into the prompt | **the cost comparison**: the whole corpus is ~1,100 words, so this is cheap here. It must be in the paper if the paper argues RAG is cheaper than "pure LLM". |

All systems use the same generator model, temperature 0, seed 42, the same prompt template, k = 3 and threshold 0.3.
The engine's silent extractive fallback is disabled during evaluation: if the LLM fails, the row is recorded as an
error and excluded (with a count), never replaced by copied context.

## Test set — `benchmark/sop_benchmark_v1.json`

40 questions written from the SOP PDFs (not generated by any evaluated system, not reused from `datasets/train_*.json`):

| Category | n | What it tests |
|---|---|---|
| procedural | 11 | full step order and actors (7 formal + 4 informal student phrasing) |
| actor | 7 | who signs / checks / receives |
| documents | 7 | required documents and signatures |
| time_location | 7 | durations, where to pick up, which system |
| cross_sop | 3 | confusing two SOPs (cross-contamination) |
| unanswerable | 5 | information that is NOT in any SOP — correct behaviour is to say so |

**Before reporting, verify every item**: open the matching PDF, check `reference`, `must_include` and (for
procedural items) the gold `steps` in `procedures`, then set `"verified": true`. Ideally ask an FSM academic
officer to check the procedural ones. Run with `--require-verified` for the final numbers and report how many
items were verified.

`python evaluate_benchmark.py check-leakage` confirms no question overlaps the fine-tuning questions
(ROUGE-L ≥ 0.5 is flagged).

## Metrics

Deterministic (no LLM, fully reproducible):

* **Key-Fact Recall (KFR)** – share of required facts (`must_include`) present in the answer.
* **ROUGE-1/2/L** – F1 against the reference (no English stemmer).
* **Step coverage / TIR / AMR** – for procedural items, each gold step is aligned to the answer line/clause that
  matches most of its keywords. TIR = share of aligned step pairs in the wrong order. AMR = share of attributed steps
  credited to the wrong official. Unattributed steps (no official named) are reported separately.
  Check the alignment by hand on a sample using `step_alignment_audit.csv` and report the agreement rate.
* **Refusal accuracy** (unanswerable items) and **false-refusal rate** (answerable items).
* **Latency** (wall clock, after warm-up) and **prompt / completion tokens** (from Ollama).

LLM-judged (optional, `--ragas`): Ragas Faithfulness (against the context the generator actually received — this
matters for Workflow GraphRAG, whose DAG context is not in the returned chunks), Answer Relevancy, Context Recall.
Use a judge model **different from the generator** (e.g. generator `gemma4:e2b`, judge `llama3.1:8b` or larger) and
name it in the paper.

Statistics: 95% bootstrap CIs (10,000 resamples) per system; paired Wilcoxon signed-rank tests against Naive RAG
with Holm correction (`significance.csv`). With 40 items, report CIs and avoid claims the CIs don't support.

## How to run

```bash
pip install pytest            # once, for the tests
python -m pytest tests/test_benchmark_metrics.py -q
python evaluate_benchmark.py check-leakage

ollama pull gemma4:e2b && ollama pull llama3.1:8b
python evaluate_benchmark.py generate --run-name smoke --systems naive,workflow --limit 3   # 2-minute check
python evaluate_benchmark.py generate --run-name gemma4_v1                                 # full run, resumable
python evaluate_benchmark.py generate --run-name gemma4_v1 --retry-errors                   # redo failed calls
python evaluate_benchmark.py score --run-name gemma4_v1 --ragas --judge-model llama3.1:8b --bertscore
```

Outputs in `results/<run-name>/`: `generations.jsonl` (every answer + context), `scores_per_query.csv`,
`summary.csv`, `summary_by_category.csv`, `significance.csv`, `step_alignment_audit.csv`, `summary_table.tex`
(paste into the paper), `run_config.json` / `score_config.json` (git commit, models, versions, benchmark hash).
Commit the final run folder so every number in the paper can be traced.

## What to write in the paper

State: number of questions and how they were built; how many were verified and by whom; generator and judge models;
temperature/seed; that Ragas scores come from a local judge; CIs and tests used; that the corpus is 7 one-page SOPs
(~1,100 words) and therefore the full-context baseline is feasible; and the limitations of the keyword-based
TIR/AMR (with your manual agreement rate).
